# 保守の手順書

このゲームの問題は、各製品の公式ドキュメントを根拠にしています。ドキュメントが変われば、問題も古くなります。
この手順書は、それを人と AI（Codex など）で無理なく追いかけるための決まりです。

## 仕組み（自動で回るもの）

- **テスト**（`.github/workflows/tests.yml`）… プルリクエストのたびに `npm test` が走ります。問題の形・選択肢の長さの偏り・出典の控えの抜けを検査します。AI も有料 API も呼びません。
- **出典の点検**（`.github/workflows/source-watch.yml`）… 毎日 09:17（日本時間）に、全問題の出典 URL を開き、次の2つを調べます。
  - 開けないページ（リンク切れ）
  - 前回の控え（`data/source-snapshots.json`）から本文が変わったページ
  
  見つかったら `source-watch` ラベルの Issue を1件だけ作り、確かめるべき問題の id を書きます。結果が前回と同じなら Issue には触らず、問題が無くなれば自動で閉じます。点検はページを取得するだけで、AI は使いません。

## Issue が立ったときの手順

1. Issue に並んだ URL を1つずつ開く。
2. 「確かめる問題」の id を `js/data/questions-*.js` で探し、ゴウのセリフ・選択肢・解説が、今のページの内容と合っているかを読む。
3. 合っていれば何もしない。食い違っていれば、問題か解説を直す（既存の `id` は変えない）。
   - その機能がなくなった場合は、問題を直すか、同じ id のまま別の内容に差し替える。
   - ページが移転した場合は、新しい URL に出典を書き換える。
4. `npm test` がすべて通ることを確かめる。
5. `node scripts/check-sources.mjs --update` で控えを今の内容にそろえる。
6. プルリクエストを出す。説明に「確かめた問題の id」と「直した／直さなかった理由」を書く。

本文の変化には、見た目だけの変更（誤字修正・並べ替えなど）も含まれます。問題に関係ない変化なら、手順 5 と 6 だけで構いません。

## Codex に頼むとき

リポジトリの `AGENTS.md` に作業ルールが書いてあるので、Codex はそれを読んでから動きます。頼み方の例です。

```text
source-watch の Issue #<番号> を片付けて。docs/MAINTENANCE.md の手順どおりに、
各 URL を読んで、挙がっている問題 id の内容が今のページと合っているか確かめて。
直すのは食い違いがある問題だけ。最後に npm test と
node scripts/check-sources.mjs --update を実行して、確かめた id と結果をまとめて。
```

- 始める前と終わった後に `git status` で変更を確かめ、必要ならコミットして戻れるようにしておきます（Codex の公式ドキュメントも、作業の前後に Git のチェックポイントを作ることを勧めています）。
- 仕上がったら Codex の `/review` で変更を見直させ、最後は人が差分を読んでからプルリクエストを出します。
- 出典のページを読むにはネット接続が要ります。Codex は既定でネットを使う前に許可を求めるので、許可するのは公式ドキュメントのサイトだけにします。

## 定期的にやること

- **月に1回** … 新しい Issue や外部からのプルリクエストがたまっていないかを見る。
- **店を足すとき** … `docs/CONTENT_GUIDE.md` に従って20問をそろえ、`stores.js`・`questionPools.js`・`introScripts.js` に登録する。

## やらないこと

- テストや自動の点検で、AI や有料 API を呼ばない。
- `main` に直接 push しない。変更はすべてプルリクエストで入れる。
